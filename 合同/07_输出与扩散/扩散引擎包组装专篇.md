## 一、概述（What）

### 1.1 本文件管什么

低膜 **已经渲染成** `03_工程底模.mp4` 之后，下一环不是再改通道，而是 **组装送扩散引擎的完整包**。

本文定义五类输入如何汇合、各自写进哪些文件、Wan 节点怎么接线：

| 输入 | 是什么 | 落盘 / 送 Wan |
|------|--------|---------------|
| **工程底膜 MP4** | 150 帧 RGB 控制视频 | `03_工程底模.mp4` → `control_video` |
| **客户自然语言** | 客户原话中的 **叙事 action**（如「跑回笼子再回头看」） | `04` 的 `## 叙事` → 拼入 `wan_positive.txt` |

| **反向提示词** | 画质/同步/身份禁区 | `04` 的 `## 负向 Prompt` → `wan_negative.txt` |
| **底膜解读 / 扩散节拍表** | 12 通道关键帧 **翻译成人话**（导演语义指令） | `04` 的 `## 扩散节拍表`（= `05` 全文）→ `wan_positive` 中段 |

> 这一路的命名、编译链、与 MP4 分工见 **[`扩散节拍表导读.md`](扩散节拍表导读.md)**。

另：**客户参考照** → `start_image.jpg`（外观锚点，不进 Prompt 正文）。

### 1.2 与 Pomot 的关系


**本专篇管的是最后一环**：MP4 与 04/wan± **同 revision 打包**。  
Pomot 的 `assembler` **只出文本**；MP4 由 `export` 或 `render-preview` 触发 `_render_opencv_video()`。

## 二、理论依据（Theory）

### 2.1 扩散引擎需要「像素 + 语义」双路

Wan Fun Control 同时吃：

| 路 | 载体 | 扩散模型读到什么 |
|----|------|------------------|
| **像素路** | `03_工程底模.mp4` | 眼眶/眉（耳）/瞳孔 **在哪、怎么动** |
| **语义路** | `wan_positive` + `wan_negative` | **演什么戏、什么情绪、不要什么** |

只有 MP4、没有文本 → 几何对但 **情绪方向可能错**（凶/媚/委屈混淆）。  
只有文本、没有 MP4 → 有故事但 **眉眼节奏不可控**。

### 2.2 「底膜解读」的两层含义

合同里 **底膜解读** = 告诉扩散模型 **如何理解控制信号**，分两层：

#### 层 A · 像素编码（MP4 本身）

黑底 RGB 硬边缘视频，三色各管一个解剖系统（与 MP4 伴生的 **隐式约定**，必要时可在运维文档中口头说明）：

| 色彩 | 解剖 | 主要通道 |
|------|------|----------|
| **R** 红 | 上下眼睑闭合环 | `blink`, `squint`, `lid_upper`, `lid_lower` |
| **G** 绿 | 眉脊 / 耳廓（猫狗） | `eyebrow`, `brow_raise` |
| **B** 蓝 | 虹膜 + 瞳孔 | `pupil_x/y`, `pupil_scale`, `iris_scale`, `cornea_bulge` |

详见 [`工程底膜合同.md`](../06_工程底膜/工程底膜合同.md) §2.2、[`12通道到底膜MP4专篇.md`](../06_工程底膜/12通道到底膜MP4专篇.md) §2.3。

#### 层 B · 通道语义说明书（嵌入 04 的正文）

由 `rhythm_compiler.build_metronome_text()` 从 **同一份** `02_烘焙.channel_tracks` 自动生成，包含：

```text
① 文件头（情绪、物种、形态）
② ## 全局阶段（蓄力→启动→保持→缓和）
③ ## 各通道脉冲（每通道 t,v + → 节拍：语义 hint）
④ ## 时间轴汇合
⑤ ## 给扩散的硬约束（摘要）（如 DOG_CONSTRAINT）
⑥ ## 出厂质检（若有）
```

示例（狗 `pupil_x`）：

```text
- **pupil_x**（视线左右）: t0=0.0, t49=0.737, …
  → 节拍：扫视方向；牵动注视与头部微转暗示
```

**这就是「底膜解读」在 Prompt 里的正式载体** — 不是手写段落，而是 **02 数值的自动翻译**，保证与 MP4 帧轴一致。

### 2.3 客户自然语言在包里的位置

客户门户输入的 **整句 NL** 在 Pomot 里被拆成：

| 字段 | 去向 | 是否进 Wan positive |
|------|------|----------------------|
| `action`（叙事） | `04` → `## 叙事` | ✅ 原文拼入 `wan_positive` |
| `emotion`（情绪词） | 路由 → 预设 → 02/正向段 | ✅ 经 `EMOTION_VISUAL_PROMPTS` 等 |
| 整句 `nl` | `客户资料.json` → `creative.nl` | ❌ 不直接进 CLIP（防 LLM 污染） |

⚠️ **叙事段禁止 LLM 改写** — 必须 `nl_splitter.action` 原文。

## 三、为什么这样做（Why）

### 3.1 关键决策

| 决策 | 备选 | 选择 | 理由 |
|------|------|------|------|
| 组装触发点 | Pomot 内嵌 / 独立 export | **export 时渲染+打包** | MP4 重算贵；04 可多次预览后再渲 |
| 底膜解读载体 | 单独 `底膜解读.txt` / 嵌入 04 | **嵌入 `## 扩散节拍表`** | 与 05 同源，避免第三份文本漂移 |
| wan_positive 组成 | 仅正向 / 正向+节拍+叙事 | **三段拼接** | CLIP 需要约束（正向）+ 精确节拍（解读）+ 故事（叙事） |
| revision 绑定 | 文件名版本 / JSON revision | **`02.revision` == `03.meta.baked_revision`** | 防止旧 MP4 配新 Prompt |

### 3.2 历史教训

| 问题 | 根因 | 规则 |
|------|------|------|
| Wan 画面不同步 | MP4 与 04 不同 revision | export 必须同批生成或校验 revision |
| 节拍表与线条图对不上 | 手写 04 | 底膜解读 **只许** 来自 `rhythm_compiler` |
| 客户故事被改写成「悲伤的狗」 | LLM 改写叙事 | `## 叙事` = action 原文 |
| 以为 Pomot 会出 MP4 | 文档与代码不一致 | assembler **不渲染**；MP4 在 export |

## 四、怎么实现（How）

### 4.1 端到端组装流

```text
┌─ 前置（已完成）─────────────────────────────────────────┐
│  Pomot round1/round2 → 02_烘焙.json + 04 草稿            │
│  render-preview 或 export → 03_工程底模.mp4              │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─ 本环节：扩散引擎包组装 ─────────────────────────────────┐
│  输入：                                                  │
│    · baked_json（02，channel_tracks 真源）               │
│    · action（客户叙事，来自 split 或 export body）        │
│    · species / breed / emotion 元信息                    │
│                                                          │
│  ① DiffusionPromptAssembler.assemble()                 │
│       ├─ _build_positive_prompt()  → 正向提示词          │
│       ├─ _build_beat_text()        → 底膜解读（节拍表）  │
│       ├─ customer_action           → 叙事（自然语言）    │
│       └─ _build_negative_prompt()  → 反向提示词          │
│     → 04_Prompt.txt（五段归档）                          │
│                                                          │
│  ② split_for_wan(04)                                     │
│       wan_positive = 正向 + 扩散节拍表 + 叙事            │
│       wan_negative = 负向段                              │
│                                                          │
│  ③ build_diffusion_bundle()                              │
│     复制：03 + 04 + wan± + start_image + manifest        │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
              Wan：control_video + positive + negative + start_image
```

### 4.2 扩散引擎包目录结构

路径：`客户资产库/客户_{cid}/项目_{pid}/输出/扩散引擎包/`

| 文件 | 来源 | Wan 接线 |
|------|------|----------|
| `03_工程底模.mp4` | `_render_opencv_video()` | **control_video** |
| `04_Prompt.txt` | `assembler.assemble()` | 归档用全文 |
| `wan_positive.txt` | `split_for_wan()` | **positive CLIP** |
| `wan_negative.txt` | `split_for_wan()` | **negative CLIP** |
| `start_image.jpg` | 客户参考照 | **start_image / IP-Adapter** |
| `manifest.json` | `build_diffusion_bundle()` | `ready_for_diffusion` 布尔 |
| `客户资料.json` | `save_project_profile()` | 含 `creative.nl` / `action` |

`manifest.json` 关键字段：

```json
{
  "schema": "diffusion_bundle_v1",
  "ready_for_diffusion": true,
  "files": { "03_工程底模.mp4": "...", "wan_positive.txt": "..." },
  "usage": "整包 scp 到 AutoDL；start_image + 03 MP4 + wan± 进 Wan Fun Control"
}
```

### 4.3 五类输入 → 04 五段映射

| 用户说的 | 04 段落 | wan 去向 |

## 六、增量修改原则

1. **底膜解读只从 02 编译** — 禁止手写节拍数值进 04  
2. **MP4 与 04 必须同 revision 出口** — 改 02 后必须 re-export  
3. **不把 02 JSON 送进 Wan** — 02 只是机器真源  
4. **若新增「独立底膜解读文件」** — 必须与 `## 扩散节拍表` 字节级同源，避免双真源  
5. **修改前读** [`扩散引擎提示词拼装规范.md`](扩散引擎提示词拼装规范.md) §4.8 Wan 接线
