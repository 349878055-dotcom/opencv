# contracts 合同规范 — 统一模板

> **每个合同都是一份"有依据的工程决策记录"** — 解释**是什么**、**理论依据是什么**、**为什么这么做**、**怎么实现**、**检查点是什么**。
>
> 所有 `contracts/` 下的文件必须遵守本文定义的格式。新合同以此为模板填空。

---

## 一、合同必须回答的五个问题

每个合同文件必须包含以下五个部分，**顺序不可调换**：

```
┌─ 1. 概述（What）── 这个合同管什么？边界在哪？
│
├─ 2. 理论依据（Theory）── 上游理论/物理/数学依据是什么？
│      ↘ 每个设计决策都要问：我的依据在哪？
│
├─ 3. 为什么这样做（Why）── 对比了哪些方案？为什么选这个？
│      ↘ 踩过什么坑 → 形成什么规则
│
├─ 4. 怎么实现（How）── 工程细节：输入/输出/公式/常量/代码映射
│
└─ 5. 检查点（Checkpoints）── 验收条件、测试方法、合格标准
```

---

## 二、各部分详细要求

### §1 概述（What）

**目的**：让读者在 30 秒内知道这个合同管什么、不管什么。

**必须包含**：

| 要素 | 要求 |
|------|------|
| 管线位置 | 上一步是什么、下一步是什么、本环节在哪 |
| 本文件用途 | 一句话说明这个文件的目的 |
| 管辖范围 | 这个合同管什么 |
| 边界（非管辖） | 明确什么**不**属于本合同（❌ 列举） |
| 引用兄弟合同 | 列举与本合同相关的其他合同文件 |

### §2 理论依据（Theory）

**目的**：回答"为什么这个环节存在" — 从物理、数学、工程、上游约束中找到依据。

**形式**：列举该环节依赖的**上游理论**，并说明该理论如何约束本环节的设计。

**示例**：

```
理论依据链：
  ① 扩散模型的 conditioning 输入必须是像素级图像（Wan 架构约束）
  ② 解剖学上眼眶、眉毛、瞳孔是三个独立运动系统 → 需要独立编码
  ③ 数字化表达需要 0-noise 保证帧间稳定性 → 推导出 LINE_8
```

**关键原则**：**没有无依据的决策**。每个设计要素都要在"理论依据"中溯源。

### §3 为什么这样做（Why）

**目的**：记录设计决策过程。**特别是踩过的坑**。

**必须包含**：

| 要素 | 要求 |
|------|------|
| 关键决策 | 列举该环节最重要的 3-5 个设计决策 |
| 备选方案 | 每个决策对比了哪些方案 |
| 选择理由 | 为什么选这个方案 |
| 历史教训 | 踩过的坑 → 形成的规则（用 ⚠️ 标注） |

**示例**：

```
决策：眼睑变形用"标准抛物线公式"而非"三角网格 warp"
  备选 1：三角网格 warp → 产生 C1 不连续毛刺（❌ 弃用）
  备选 2：5 点 polylines → 方块眼（❌ 弃用）
  备选 3：7 点抛物线拟合 → 拟合误差导致眼角跑偏（❌ 弃用）
  选择：标准抛物线公式 → 精确匹配底图，天然闭合（✅ 正选）
```

### §4 怎么实现（How）

**目的**：工程实现细节 — 让工程师或 AI 能直接照此实现。

**必须包含**：

| 要素 | 要求 |
|------|------|
| 输入规格 | 数据来源、格式、约束 |
| 输出规格 | 数据格式、分辨率、色彩协议 |
| 核心公式/算法 | 关键的数学公式或算法伪代码 |
| 关键常量 | 所有可调常量的含义和默认值 |
| 代码映射 | 哪个代码文件、哪个函数负责什么 |
| 调用关系 | 谁调用本模块、本模块调用谁 |

### §5 检查点（Checkpoints）

**目的**：验收标准 — 怎么验证这个环节做对了。

**必须包含**：

| 要素 | 要求 |
|------|------|
| 检查项 | 检查什么 |
| 测试方法 | 用什么方法测（视觉/数值/自动化） |
| 合格标准 | 达到什么值才算通过 |

**格式**：

```
| 检查项 | 测试方法 | 合格标准 | 优先级 |
|--------|---------|---------|--------|
| ...    | ...     | ...     | P0/P1 |
```

## 三、文件命名规则

| 类别 | 命名格式 | 示例 |
|------|---------|------|
| 合同规范（本文件） | `合同规范.md` | `contracts/合同规范.md` |
| 总纲合同 | 按内容命名 | `全量帧指令集规范.md` |
| 情绪合同 | 中文情绪名 | `魅惑勾人.md` |
| 工程合同 | `工程{主题}合同.md` + `{主题}驱动规范.md` | `工程底膜合同.md`, `工程底膜驱动规范.md` |
| 接口合同 | 按接口名命名 | `UI设计原则.md` |

---

## 四、文档格式规范

| 项 | 要求 |
|----|------|
| 标题层级 | `#` 文件标题 → `##` 五部分主标题 → `###` 子标题 → `####` 细项 |
| 代码引用 | 文件名：[`文件名`](相对路径)；函数名：[`函数名()`](相对路径:行号) |
| 术语加粗 | 首次出现的核心术语用 `**粗体**` |
| 警告标注 | ⚠️ 踩过的坑 / 禁止行为；💥 绝对禁止 |
| 引用兄弟合同 | 本文件开头必须列出引用和兄弟合同 |
| 修改记录 | 每次修改在文件末尾追加一行 `| YYYY-MM-DD | 改了什么 | 原因 |` |

## 五、写合同时的思维检查清单

写每个部分前，问自己：

```
□ §1 概述：读者 30 秒能知道这是关于什么的吗？
□ §2 理论依据：这个决策有没有物理/数学/上游依据在支撑？
     — 如果没有依据 → 不要写进合同，先找依据
     — 如果找不到依据 → 重新审视这个决策是否合理
□ §3 为什么：我说的"为什么"不是"因为需要"，而是"对比了哪些方案"？
     — "因为需要"不是理由，谁都知道需要
     — "A方案有xxx问题，B方案有xxx问题，所以选C" 才是理由
□ §4 怎么实现：信息量够让另一个工程师照着写代码吗？
□ §5 检查点：每项检查是可以通过程序或肉眼验证的吗？
